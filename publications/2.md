## 1. A ideia em uma frase

> **Conceitual = o que o negócio precisa. Lógico = como os dados se organizam. Físico = como isso vira um banco de verdade.**

Os três níveis descrevem **a mesma coisa**, cada um com mais detalhe técnico que o anterior.

## 2. A analogia da casa

| Etapa da casa | Quem usa | Equivalente em dados |
|---|---|---|
| **Esboço com o cliente:** "quero 3 quartos, cozinha integrada, quintal" | Cliente e arquiteto | **Conceitual** |
| **Planta baixa:** medidas, paredes, portas, ligação entre os cômodos | Arquiteto | **Lógico** |
| **Projeto executivo:** tipo de tijolo, bitola do cano, marca da fiação | Engenheiro e pedreiro | **Físico** |

O cliente não precisa saber a bitola do cano para aprovar a casa. O pedreiro não constrói a partir do esboço. Cada nível conversa com um público diferente.

## 3. Os três níveis lado a lado

| | Conceitual | Lógico | Físico |
|---|---|---|---|
| **Pergunta que responde** | O que existe no negócio? | Como organizar em tabelas? | Como criar no banco X? |
| **Público** | Áreas de negócio | Analistas e administradores de dados | DBAs e desenvolvedores |
| **Elementos** | Entidades, atributos, relacionamentos | Tabelas, colunas, PK, FK | Tipos reais, índices, partições, constraints |
| **Depende do banco?** | Não | Não | Sim (Oracle, SQL Server, DB2...) |
| **Normalização** | Não se aplica | Aplicada aqui | Pode haver desnormalização por performance |
| **Resultado** | Diagrama para validar com o negócio | Estrutura de tabelas | Script de criação (DDL) |

## 4. Vocabulário essencial

| Termo | Em palavras simples | Exemplo |
|---|---|---|
| **Entidade** | Uma "coisa" sobre a qual guardamos informação | Participante, Curso |
| **Atributo** | Uma característica da entidade | Nome, CPF, carga horária |
| **Relacionamento** | Como duas entidades se ligam | Participante **se inscreve em** Curso |
| **Cardinalidade** | Quantos de um lado se ligam a quantos do outro | 1:1, 1:N, N:N |
| **Opcionalidade** | Se a ligação é obrigatória ou não | Todo curso **precisa** de instrutor? |
| **Chave primária (PK)** | O que identifica cada linha sem confusão | `id_participante` |
| **Chave estrangeira (FK)** | Coluna que aponta para outra tabela | `curso.id_instrutor` |
| **Chave composta** | PK formada por duas ou mais colunas | `(id_participante, id_curso)` |
| **Chave natural** | Identificador que vem do negócio | CPF |
| **Chave surrogate** | Identificador artificial, criado pelo sistema | Número sequencial |

### Cardinalidade em exemplos do dia a dia

| Tipo | Leitura | Exemplo |
|---|---|---|
| **1:1** | Um para um | Uma pessoa tem um passaporte; um passaporte é de uma pessoa |
| **1:N** | Um para muitos | Um instrutor dá vários cursos; cada curso tem um instrutor |
| **N:N** | Muitos para muitos | Um participante faz vários cursos; um curso tem vários participantes |

### Opcionalidade

Cardinalidade fala do **máximo**. Opcionalidade fala do **mínimo**:

- **0** = opcional: um participante **pode** não ter nenhuma inscrição ainda.
- **1** = obrigatório: um curso **precisa** ter um instrutor.

No modelo físico, isso decide se a chave estrangeira aceita ficar vazia (`NULL`) ou não (`NOT NULL`).

## 5. Nível 1: Modelo conceitual

### Objetivo

Entender e registrar **o negócio**, numa linguagem que qualquer pessoa da área consiga validar. Não tem tabela, tipo de dado nem nome técnico.

### Como chegar nele

Conversando com a área de negócio e prestando atenção nas palavras:

- **Substantivos** costumam virar **entidades**: participante, curso, instrutor, sala.
- **Verbos** costumam virar **relacionamentos**: se inscreve, ministra, acontece em.
- **Características** viram **atributos**: nome, e-mail, capacidade da sala.

### Exemplo: sistema de cursos

Regras levantadas com o negócio:

1. Um participante pode se inscrever em vários cursos, e um curso recebe vários participantes.
2. Cada curso tem um instrutor; um instrutor pode dar vários cursos.
3. Cada curso acontece em uma sala; uma sala recebe vários cursos.

```text
PARTICIPANTE ──(se inscreve em)── CURSO           N:N
INSTRUTOR    ──(ministra)──────── CURSO           1:N
SALA         ──(recebe)────────── CURSO           1:N
```

Entidades e atributos principais:

| Entidade | Atributos |
|---|---|
| Participante | Nome, CPF, e-mail |
| Curso | Nome, carga horária |
| Instrutor | Nome, especialidade |
| Sala | Nome, capacidade |

📝 **Para lembrar:** se a área de negócio não entende o diagrama, ele não é conceitual.

## 6. Nível 2: Modelo lógico

### Objetivo

Transformar o conceitual em uma **estrutura de tabelas**, ainda sem escolher o banco de dados.

### O que acontece nesta etapa

1. **Cada entidade vira uma tabela.**
2. **Cada tabela ganha uma chave primária.**
3. **Relacionamentos 1:N viram chave estrangeira** no lado do "N".
4. **Relacionamentos N:N viram uma tabela associativa** no meio.
5. **Aplica-se a normalização** (1FN, 2FN, 3FN) para eliminar repetição.

### Regra de ouro dos relacionamentos

| No conceitual | No lógico |
|---|---|
| **1:N** | A FK vai para a tabela do lado **N** (o curso guarda quem é seu instrutor) |
| **N:N** | Cria-se uma **tabela associativa** com as duas chaves |
| **1:1** | A FK vai para um dos lados, normalmente o opcional, com restrição de valor único |

**Por que a FK fica no lado N?** Um curso tem **um** instrutor, então cabe uma coluna `id_instrutor` em cada curso. Se fosse ao contrário, o instrutor precisaria de uma coluna para cada curso que dá, o que quebra a 1FN.

**Por que o N:N vira tabela?** Uma coluna só aponta para uma linha. Para guardar "Ana fez Excel e Power BI", é preciso uma tabela que registre cada par participante-curso.

### Exemplo: sistema de cursos

```text
PARTICIPANTE (id_participante PK, nome, cpf, email)
INSTRUTOR    (id_instrutor PK, nome, especialidade)
SALA         (id_sala PK, nome, capacidade)
CURSO        (id_curso PK, nome, carga_horaria, id_instrutor FK, id_sala FK)
INSCRICAO    (id_participante PK/FK, id_curso PK/FK, data_inscricao, situacao)
```

```text
INSTRUTOR    1 ──< N  CURSO
SALA         1 ──< N  CURSO
PARTICIPANTE 1 ──< N  INSCRICAO  N >── 1  CURSO
```

O que vale observar:

- **INSCRICAO** é a tabela associativa que resolve o N:N entre participante e curso.
- O N:N se desfez em **dois relacionamentos 1:N**.
- `data_inscricao` e `situacao` ficam em INSCRICAO porque dependem do **par** participante + curso.
- A sala ficou em CURSO, e não em INSCRICAO: se o curso mudar de sala, altera-se uma linha só.
- O CPF não é a PK, mas deve ser único. Ele é uma **chave alternativa**.

📝 **Para lembrar:** no lógico tudo vira tabela e chave, mas ainda não existe "Oracle" nem "SQL Server".

## 7. Nível 3: Modelo físico

### Objetivo

Adaptar o modelo lógico a **um banco de dados específico**, com tudo o que ele precisa para ser criado e funcionar bem.

### O que se decide aqui

| Decisão | Exemplo |
|---|---|
| **Tipos de dado reais** | `VARCHAR2(100)` no Oracle, `NVARCHAR(100)` no SQL Server |
| **Nomes físicos** | Padrões como `TB_CURSO`, `CD_CURSO`, `NM_CURSO` |
| **Restrições** | `NOT NULL`, `UNIQUE`, `CHECK`, `DEFAULT` |
| **Índices** | Índice nas FKs e nas colunas mais usadas em filtros |
| **Particionamento** | Dividir tabelas grandes, por exemplo por data |
| **Armazenamento** | Tablespaces, compressão |
| **Desnormalização** | Só quando a performance justificar |

### Exemplo: script de criação (Oracle)

```sql
CREATE TABLE curso (
    id_curso       NUMBER(10)     PRIMARY KEY,
    nome           VARCHAR2(100)  NOT NULL,
    carga_horaria  NUMBER(4)      CHECK (carga_horaria > 0),
    id_instrutor   NUMBER(10)     NOT NULL REFERENCES instrutor (id_instrutor),
    id_sala        NUMBER(10)     NOT NULL REFERENCES sala (id_sala)
);

CREATE TABLE inscricao (
    id_participante  NUMBER(10)    REFERENCES participante (id_participante),
    id_curso         NUMBER(10)    REFERENCES curso (id_curso),
    data_inscricao   DATE          DEFAULT SYSDATE NOT NULL,
    situacao         VARCHAR2(20)  CHECK (situacao IN ('CONFIRMADA', 'CANCELADA')),
    PRIMARY KEY (id_participante, id_curso)
);

CREATE INDEX ix_curso_instrutor ON curso (id_instrutor);
```

Repare em como as decisões do físico aparecem no script:

- `NOT NULL` em `id_instrutor` vem da **opcionalidade**: todo curso precisa de instrutor.
- `CHECK` transforma **regras de negócio** em regra do banco.
- O **índice** na FK acelera consultas como "quais cursos esse instrutor dá?".

### O mesmo modelo em bancos diferentes

O lógico é um só. O físico muda conforme o banco:

| Lógico | Oracle | SQL Server |
|---|---|---|
| Texto | `VARCHAR2(100)` | `VARCHAR(100)` / `NVARCHAR(100)` |
| Número inteiro | `NUMBER(10)` | `INT` |
| Data | `DATE` | `DATE` / `DATETIME2` |
| Identificador automático | `SEQUENCE` ou `IDENTITY` | `IDENTITY` |

📝 **Para lembrar:** o físico é o único nível que "sabe" qual banco vai ser usado.

## 8. Casos especiais de modelagem

### Entidade fraca e relacionamento identificador

Algumas coisas só existem por causa de outra. Um **item de pedido** não existe sem o **pedido**.

- **Entidade fraca:** depende de outra para existir.
- **Relacionamento identificador:** a chave do "pai" faz parte da chave do "filho".

```text
PEDIDO      (nr_pedido PK)
ITEM_PEDIDO (nr_pedido PK/FK, nr_item PK, produto, quantidade)
```

O item 3 do pedido 1050 é identificado por `(1050, 3)`.

Quando a FK **não** faz parte da PK (como `id_instrutor` em CURSO), o relacionamento é **não identificador**.

### Generalização e especialização

Quando várias entidades compartilham características, mas cada uma tem algo próprio:

```text
PESSOA (id, nome, email)
  ├── PESSOA_FISICA   (cpf, data_nascimento)
  └── PESSOA_JURIDICA (cnpj, razao_social)
```

No físico, há três formas de implementar:

| Forma | Como fica | Prós e contras |
|---|---|---|
| Tabela única | Tudo em PESSOA, com uma coluna "tipo" | Simples, mas com muitas colunas vazias |
| Uma tabela por tipo | PESSOA_FISICA e PESSOA_JURIDICA separadas, repetindo nome e e-mail | Sem colunas vazias, mas consultas gerais ficam mais trabalhosas |
| Pai + filhos | PESSOA com o comum, e tabelas filhas com o específico | Mais organizado, porém com mais junções |

### Auto-relacionamento

Uma entidade que se liga a ela mesma. Exemplo: o gestor de um funcionário também é um funcionário.

```text
FUNCIONARIO (id_funcionario PK, nome, id_gestor FK → FUNCIONARIO)
```

### Atributo multivalorado

Um participante com vários telefones não ganha colunas "telefone1, telefone2". Vira tabela filha:

```text
TELEFONE_PARTICIPANTE (id_participante PK/FK, telefone PK)
```

### Chave natural x chave surrogate

| | Chave natural | Chave surrogate |
|---|---|---|
| **O que é** | Vem do negócio (CPF, placa) | Criada pelo sistema (1, 2, 3...) |
| **Vantagem** | Tem significado | Estável, compacta, nunca muda |
| **Risco** | Pode mudar ou vir com formato diferente | Não tem significado sozinha |

Prática comum: **surrogate como PK** e a natural como **UNIQUE**, garantindo a regra de negócio.

## 9. Os três níveis no PowerDesigner

O PowerDesigner é uma ferramenta de modelagem que trabalha exatamente com esses três níveis:

| Nível | Sigla no PowerDesigner | Nome |
|---|---|---|
| Conceitual | **CDM** | Conceptual Data Model |
| Lógico | **LDM** | Logical Data Model |
| Físico | **PDM** | Physical Data Model |

```text
CDM  →  LDM  →  PDM  →  Script DDL  →  Banco de dados
```

| Caminho | Nome | Para que serve |
|---|---|---|
| Do modelo para o banco | **Engenharia direta (forward engineering)** | Criar um banco novo a partir do modelo |
| Do banco para o modelo | **Engenharia reversa** | Documentar um banco que já existe, como em sistemas legados |

A ferramenta mantém o vínculo entre os níveis: dá para saber de qual entidade de negócio veio cada tabela física.

## 10. Como explicar em uma entrevista

### Resposta curta (20 segundos)

> "O conceitual representa o negócio, com entidades e relacionamentos, sem tecnologia. O lógico organiza isso em tabelas, chaves e normalização, ainda sem um banco específico. O físico implementa em um banco real, com tipos de dado, índices, restrições e partições, e é dele que sai o script de criação."

### Com exemplo (40 segundos)

> "Num sistema de cursos, no conceitual eu tenho Participante e Curso com um relacionamento muitos-para-muitos. No lógico, isso vira uma tabela de inscrição com as duas chaves, porque banco relacional não implementa N:N direto. No físico, eu defino os tipos para o banco escolhido, coloco NOT NULL onde o relacionamento é obrigatório e crio índices nas chaves estrangeiras."

### Perguntas que podem aparecer

| Pergunta | Resposta curta |
|---|---|
| Por que separar em três níveis? | Cada nível conversa com um público e permite trocar o banco sem refazer o entendimento do negócio |
| Onde entra a normalização? | No modelo lógico |
| Onde entram os índices? | No modelo físico |
| Como um N:N vira tabela? | Com uma tabela associativa que guarda as duas chaves |
| Em 1:N, a FK fica em qual lado? | No lado N |
| O que é engenharia reversa? | Gerar o modelo a partir de um banco existente |

### Exercício 5

Modele nos três níveis: "Um autor escreve vários livros e um livro pode ter vários autores. Cada livro pertence a uma editora; uma editora publica vários livros."

<details>
<summary>Ver resposta</summary>

**Conceitual**

```text
AUTOR   ──(escreve)──  LIVRO    N:N
EDITORA ──(publica)──  LIVRO    1:N
```

**Lógico**

```text
EDITORA     (id_editora PK, nome)
LIVRO       (id_livro PK, titulo, isbn, id_editora FK)
AUTOR       (id_autor PK, nome)
LIVRO_AUTOR (id_livro PK/FK, id_autor PK/FK)
```

**Físico** (exemplo de decisões)

- `isbn` com restrição `UNIQUE` (chave alternativa)
- `id_editora` com `NOT NULL` (todo livro tem editora)
- Índice em `livro.id_editora`
- Tipos definidos para o banco escolhido

</details>

## 12. Cola para revisão

| Nível | Uma palavra | O que tem | O que não tem |
|---|---|---|---|
| **Conceitual** | Negócio | Entidades, atributos, relacionamentos, cardinalidade | Tabelas, tipos, banco |
| **Lógico** | Estrutura | Tabelas, PK, FK, associativas, normalização | Tipos específicos de um banco |
| **Físico** | Implementação | Tipos reais, índices, constraints, partições, DDL | Nada a esconder: é o banco real |

### Regras para não esquecer

- **1:N** → FK no lado N.
- **N:N** → tabela associativa, que vira dois 1:N.
- **Opcionalidade obrigatória** → `NOT NULL` no físico.
- **Normalização** → acontece no lógico.
- **Índices e partições** → acontecem no físico.
- **Chave natural** → normalmente vira `UNIQUE`; a PK costuma ser surrogate.
- **PowerDesigner:** CDM = conceitual, LDM = lógico, PDM = físico.
