## 4. Revisão rápida para a véspera

### Modelagem

| Conceito | O que é | Exemplo |
| --- | --- | --- |
| Modelo conceitual | Visão de negócio, sem tecnologia | "Cliente faz Pedido" |
| Modelo lógico | Estrutura em tabelas, chaves e relacionamentos, sem banco específico | `CLIENTE(id_cliente PK, nome)` |
| Modelo físico | Implementação em um SGBD real | `CREATE TABLE cliente (id_cliente NUMBER(10) PRIMARY KEY, ...)` |
| Cardinalidade | Quantas ocorrências se relacionam | Um cliente tem **vários** pedidos (1:N) |
| Opcionalidade | Se o relacionamento é obrigatório | Todo pedido **precisa** ter cliente; um cliente **pode** não ter pedido |
| PK (chave primária) | Identifica cada linha de forma única | `id_cliente` |
| FK (chave estrangeira) | Coluna que referencia a PK de outra tabela | `pedido.id_cliente` → `cliente.id_cliente` |
| Chave composta | PK formada por mais de uma coluna | `ITEM_PEDIDO(nr_pedido, cod_produto)` |
| Chave natural | Vem do próprio negócio | CPF, placa do veículo |
| Chave surrogate | Artificial, sem significado de negócio | `id` sequencial |
| Tabela associativa | Resolve um relacionamento N:N | `MATRICULA` entre Aluno e Disciplina |
| Relacionamento 1:1 | Uma ocorrência para uma | Pessoa ↔ Passaporte |
| Relacionamento 1:N | Uma para muitas | Cliente → Pedidos |
| Relacionamento N:N | Muitas para muitas | Alunos ↔ Disciplinas |

### Regra para memorizar

- **Conceitual** = negócio
- **Lógico** = estrutura dos dados
- **Físico** = implementação no banco

### Normalização em 3 linhas

- **1FN:** um valor por campo.
- **2FN:** em chave composta, todo atributo depende da chave **inteira**.
- **3FN:** atributo não chave não depende de outro atributo **não chave**.

### PowerDesigner em 3 linhas

- CDM (conceitual) → LDM (lógico) → PDM (físico).
- Engenharia reversa: lê o banco existente e gera o modelo.
- Forward engineering: gera o script DDL a partir do modelo físico.

## 5. Exercícios resolvidos

### Exercício 1 — Relacionamento N:N

**Enunciado:** um aluno cursa várias disciplinas e uma disciplina tem vários alunos. Como representar isso no modelo lógico?

**Raciocínio:**

1. Bancos relacionais não implementam N:N diretamente: uma FK só aponta para uma linha.
2. Se eu colocar `id_disciplina` em ALUNO, cada aluno só teria uma disciplina. Se colocar `id_aluno` em DISCIPLINA, cada disciplina só teria um aluno.
3. A solução é criar uma **tabela associativa** no meio, que guarda cada par aluno-disciplina.

**Resposta:**

```text
Antes (conceitual):
ALUNO  N ────── N  DISCIPLINA

Depois (lógico):
ALUNO  1 ──< N  MATRICULA  N >── 1  DISCIPLINA

ALUNO      (id_aluno PK, nome)
DISCIPLINA (id_disciplina PK, nome)
MATRICULA  (id_aluno PK/FK, id_disciplina PK/FK, semestre, nota)
```

O N:N vira **dois relacionamentos 1:N**. A tabela associativa também é o lugar natural para atributos do relacionamento, como semestre e nota.

### Exercício 2 — Dependência transitiva (3FN)

**Enunciado:** `FUNCIONARIO(cpf, nome, cod_depto, nome_depto)`, com chave `cpf`. Qual forma normal é violada?

**Raciocínio:**

1. **1FN?** Todos os valores são atômicos. Ok.
2. **2FN?** A chave é simples (só `cpf`). Sem chave composta não existe dependência parcial. Ok.
3. **3FN?** `nome_depto` não depende diretamente de `cpf`. Ele depende de `cod_depto`, que por sua vez depende de `cpf`:

```text
cpf → cod_depto → nome_depto
```

Isso é uma **dependência transitiva**: um atributo não chave determinando outro atributo não chave.

**Problema prático:** se o departamento tem 200 funcionários, o nome dele se repete 200 vezes. Renomear o departamento exige atualizar 200 linhas.

**Resposta:** viola a **3FN**. Separando:

```text
FUNCIONARIO  (cpf PK, nome, cod_depto FK)
DEPARTAMENTO (cod_depto PK, nome_depto)
```

> Pegadinha comum: muita gente responde 2FN. Com chave simples, a 2FN não é violada por dependência parcial.

### Exercício 3 — Chave composta e dependência parcial (2FN)

**Enunciado:** `ITEM_PEDIDO(nr_pedido, cod_produto, qtd, descricao_produto)`, com chave composta `(nr_pedido, cod_produto)`. Qual forma normal é violada?

**Raciocínio:** com chave composta, a pergunta da 2FN é: cada atributo depende da chave **inteira**?

| Atributo | Depende de | Situação |
| --- | --- | --- |
| `qtd` | `nr_pedido` + `cod_produto` | Ok: é a quantidade daquele produto naquele pedido |
| `descricao_produto` | Só `cod_produto` | Problema: a descrição é a mesma em qualquer pedido |

`descricao_produto` depende de **parte** da chave: é uma **dependência parcial**.

**Resposta:** viola a **2FN**. Separando:

```text
PEDIDO      (nr_pedido PK, data_pedido)
PRODUTO     (cod_produto PK, descricao_produto)
ITEM_PEDIDO (nr_pedido PK/FK, cod_produto PK/FK, qtd)

PEDIDO  1 ──< N  ITEM_PEDIDO  N >── 1  PRODUTO
```

Repare que é o mesmo padrão do Exercício 1: Pedido e Produto têm um relacionamento N:N, e ITEM_PEDIDO é a tabela associativa.

> Regra para decorar: chave composta e atributo dependendo de parte dela → 2FN. Atributo não chave dependendo de outro não chave → 3FN.

## 6. Modelagem de dados

### Os três níveis

| Nível      | Objetivo              | Exemplos                    |
| ---------- | --------------------- | --------------------------- |
| Conceitual | Representar o negócio | Entidades e relacionamentos |
| Lógico     | Estruturar os dados   | Tabelas, PK, FK             |
| Físico     | Implementar no SGBD   | Tipos, índices, partições   |

- **Conceitual:** é a conversa com o negócio. Não fala de tabela nem de tipo de dado. Responde "quais coisas importam e como se relacionam?".
- **Lógico:** traduz o conceitual em estruturas relacionais: tabelas, colunas, PK, FK e normalização. Ainda é independente de banco.
- **Físico:** adapta o lógico a um SGBD específico (Oracle, SQL Server, DB2, PostgreSQL), com tipos reais, índices, partições, tablespaces e constraints. É dele que sai o script DDL.

### Cardinalidade e opcionalidade

- **Cardinalidade** é o máximo de ocorrências: 1 ou N.
- **Opcionalidade** é o mínimo: 0 (opcional) ou 1 (obrigatório).

Exemplo: "um pedido pertence a **exatamente um** cliente; um cliente tem **zero ou muitos** pedidos". No físico, a opcionalidade define se a FK aceita `NULL`.

### Chaves

| Tipo | Definição | Exemplo |
| --- | --- | --- |
| Candidata | Qualquer conjunto mínimo de colunas que identifica a linha | `cpf` ou `id_cliente` |
| Primária (PK) | A candidata escolhida como identificador oficial | `id_cliente` |
| Alternativa | Candidata que não virou PK; implementada como `UNIQUE` | `cpf` |
| Estrangeira (FK) | Referência à PK de outra tabela | `pedido.id_cliente` |
| Composta | Formada por mais de uma coluna | `(nr_pedido, cod_produto)` |
| Natural | Tem significado de negócio | CPF, CNPJ |
| Surrogate | Artificial, gerada pelo sistema | sequence, identity, UUID |

**Natural x surrogate:** a chave natural pode mudar ou ter formato inconsistente ao longo do tempo. A surrogate é estável e compacta. Uma prática comum é usar a surrogate como PK e manter a natural como `UNIQUE`, garantindo a regra de negócio.

### Relacionamento identificador e entidade fraca

- **Relacionamento identificador:** a PK do pai faz parte da PK do filho. Ex.: o item 3 do pedido 1050 é identificado por `(1050, 3)`.
- **Não identificador:** a FK fica fora da PK do filho. Ex.: `pedido.id_cliente`.
- **Entidade fraca:** só existe em função de outra. O item de pedido não existe sem o pedido.

### Generalização / especialização

Quando entidades compartilham atributos, mas têm particularidades:

```text
PESSOA (id, nome, email)
  ├── PESSOA_FISICA   (cpf, data_nascimento)
  └── PESSOA_JURIDICA (cnpj, razao_social)
```

No modelo físico há três estratégias:

| Estratégia | Como fica | Vantagem | Desvantagem |
| --- | --- | --- | --- |
| Tabela única | Uma tabela com todas as colunas e um tipo | Consultas simples | Muitas colunas nulas |
| Tabela por subtipo | Uma tabela para cada subtipo, com atributos comuns repetidos | Sem nulos | Consultas gerais exigem UNION |
| Supertipo + subtipos | Tabela comum + tabelas específicas ligadas por PK/FK | Mais normalizado | Mais joins |

### Auto-relacionamento

Uma entidade se relaciona com ela mesma:

```text
FUNCIONARIO (id_funcionario PK, nome, id_gestor FK → FUNCIONARIO.id_funcionario)
```

Usado para hierarquias (gestor e subordinado, categoria e subcategoria).

### Atributos multivalorados

Um cliente com vários telefones não deve ter `telefone1, telefone2, telefone3`. O correto é uma tabela filha:

```text
CLIENTE          (id_cliente PK, nome)
TELEFONE_CLIENTE (id_cliente PK/FK, numero PK, tipo)
```

### Notações

- **Pé de galinha (Information Engineering):** a mais comum em ferramentas de modelagem.
- **Barker** e **IDEF1X:** outras notações que aparecem em ambientes corporativos.

### Introdução à modelagem dimensional

Usada em Data Warehouse e BI, com foco em consulta e análise, não em transação.

| Conceito | Definição | Exemplo |
| --- | --- | --- |
| Fato | Evento mensurável, com métricas | Venda: valor, quantidade |
| Dimensão | Contexto do fato | Cliente, produto, data, loja |
| Modelo estrela | Fato no centro, dimensões desnormalizadas ao redor | Consultas mais simples e rápidas |
| Snowflake | Dimensões normalizadas em várias tabelas | Menos redundância, mais joins |

```text
            DIM_DATA
               |
DIM_CLIENTE — FATO_VENDA — DIM_PRODUTO
               |
            DIM_LOJA
```

**SCD (Slowly Changing Dimension):** como tratar mudanças em dimensões.

| Tipo | O que faz | Exemplo |
| --- | --- | --- |
| SCD Tipo 1 | Sobrescreve o valor antigo; não guarda histórico | Correção de nome digitado errado |
| SCD Tipo 2 | Cria nova linha com período de vigência; guarda histórico | Cliente mudou de cidade e quero analisar vendas por cidade na época |

```text
DIM_CLIENTE (sk_cliente, cpf, cidade,     data_inicio, data_fim,   atual)
             1,          111, São Paulo,  2024-01-01,  2026-03-31, N
             2,          111, Campinas,   2026-04-01,  NULL,       S
```

## 7. Normalização

Normalizar é organizar as tabelas para **eliminar redundância** e evitar inconsistências.

### Anomalias que a normalização evita

Usando a tabela não normalizada `FUNCIONARIO(cpf, nome, cod_depto, nome_depto)`:

| Anomalia | O que acontece |
| --- | --- |
| Inserção | Não consigo cadastrar um departamento novo sem ter um funcionário nele |
| Atualização | Para renomear um departamento, preciso alterar todas as linhas dos funcionários; se esquecer alguma, o dado fica inconsistente |
| Exclusão | Ao excluir o último funcionário de um departamento, perco a informação de que o departamento existe |

### Formas normais

| Forma | Regra | Exemplo de violação | Correção |
| --- | --- | --- | --- |
| 1FN | Valores atômicos, sem grupos repetidos | Coluna `telefones` = "1111, 2222" | Tabela filha de telefones |
| 2FN | 1FN + atributos dependem da chave inteira | `descricao_produto` em ITEM_PEDIDO | Mover para PRODUTO |
| 3FN | 2FN + sem dependência transitiva | `nome_depto` em FUNCIONARIO | Criar DEPARTAMENTO |
| FNBC | Todo determinante é chave candidata | Ver exemplo abaixo | Decompor pelo determinante |
| 4FN | Sem dependências multivaloradas independentes | Habilidades e idiomas na mesma tabela | Separar em duas tabelas |
| 5FN | Sem dependências de junção que gerem dados falsos | Fornecedor-peça-projeto em uma tabela só | Decompor somente se recompor sem perda |

> Chave simples → não existe dependência parcial, portanto a 2FN não é violada por dependência parcial.

### Exemplos das formas avançadas

**FNBC:** `AULA(aluno, disciplina, professor)`, chave `(aluno, disciplina)`. Cada professor ensina uma única disciplina, então `professor → disciplina`. O professor determina a disciplina, mas não é chave candidata. Isso viola a FNBC, mesmo estando na 3FN.

**4FN:** `FUNCIONARIO_PERFIL(func, habilidade, idioma)`. Habilidades e idiomas são independentes entre si, e guardá-los juntos gera combinações artificiais. Correção: `FUNC_HABILIDADE(func, habilidade)` e `FUNC_IDIOMA(func, idioma)`.

**5FN:** aparece quando uma tabela com três ou mais chaves só pode ser decomposta em três partes sem perda de informação. É raro no dia a dia; o importante é saber que existe e definir.

### Exercício completo

Tabela inicial:

```text
PEDIDO(nr_pedido, data, cpf_cliente, nome_cliente, cidade_cliente,
       cod_produto, desc_produto, preco_unit, qtd)
```

1. **1FN:** garantir uma linha por item do pedido. Chave: `(nr_pedido, cod_produto)`.
2. **2FN:** `data` e `cpf_cliente` dependem só de `nr_pedido`; `desc_produto` e `preco_unit` só de `cod_produto`.

```text
PEDIDO      (nr_pedido PK, data, cpf_cliente)
PRODUTO     (cod_produto PK, desc_produto, preco_unit)
ITEM_PEDIDO (nr_pedido PK/FK, cod_produto PK/FK, qtd, preco_praticado)
```

3. **3FN:** `nome_cliente` e `cidade_cliente` dependem de `cpf_cliente`, que não é chave de PEDIDO.

```text
CLIENTE (cpf_cliente PK, nome, cidade)
PEDIDO  (nr_pedido PK, data, cpf_cliente FK)
```

Detalhe importante: ITEM_PEDIDO guarda o **preço praticado** na venda. Não é redundância com `preco_unit`, porque o preço do produto muda com o tempo e o pedido precisa registrar o valor da época.

### Desnormalização

Desnormalizar é introduzir redundância **de propósito** para melhorar leitura. Exemplos:

- modelo estrela em Data Warehouse;
- colunas calculadas (total do pedido);
- tabelas agregadas para relatórios;
- views materializadas.

O custo é mais espaço e risco de inconsistência, que precisa ser controlado por ETL, triggers ou rotinas de atualização.

> Em sistemas transacionais, a normalização ajuda a reduzir redundância e inconsistência. Em ambientes analíticos, a desnormalização pode ser utilizada de forma controlada para melhorar consultas e facilitar análises.

## 8. PowerDesigner na prática

> Ainda não utilizei o PowerDesigner em produção. Estou estudando a ferramenta para entender seu fluxo e relacioná-lo aos conhecimentos de modelagem que já possuo.

O PowerDesigner é uma ferramenta da SAP (originalmente da Sybase) para **modelagem e documentação de dados**, muito usada em ambientes corporativos para manter modelos, padrões e metadados de forma centralizada.

### Tipos de modelo

| Sigla | Significado           | Objetivo          |
| ----- | --------------------- | ----------------- |
| CDM   | Conceptual Data Model | Modelo conceitual |
| LDM   | Logical Data Model    | Modelo lógico     |
| PDM   | Physical Data Model   | Modelo físico     |
| DMM   | Data Movement Model   | Fluxos de dados   |

A ferramenta também tem modelos orientados a objetos (OOM), de processos (BPM) e de arquitetura corporativa (EAM), menos centrais para a função de Administrador de Dados.

### Fluxo CDM → LDM → PDM

```text
CDM (negócio) → LDM (estrutura) → PDM (banco específico) → Script DDL
```

Cada modelo pode ser gerado a partir do anterior, e a ferramenta mantém o vínculo entre eles. Isso permite rastrear uma tabela física até a entidade de negócio que a originou.

### Principais recursos

| Recurso | O que faz |
| --- | --- |
| Engenharia reversa | Lê um banco existente (ou um script DDL) e gera o PDM. Útil em sistemas legados sem documentação |
| Forward engineering | Caminho inverso: do modelo para o banco |
| Geração de DDL | Gera o script `CREATE`/`ALTER` a partir do PDM, completo ou apenas com alterações |
| Compare/Merge | Compara duas versões do modelo, ou o modelo com o banco, e gera as diferenças |
| Domínios | Tipos padronizados e reutilizáveis (ex.: domínio `CPF` = `CHAR(11)` com regra de validação) |
| Dicionário de dados | Relatórios gerados a partir do modelo, com tabelas, colunas e descrições |
| Regras de negócio | Regras documentadas e associadas aos objetos do modelo |
| Name x Code | Nome de negócio ("Data de Nascimento") separado do nome físico (`DT_NASC`), com regras de conversão |
| Check Model | Valida o modelo: tabela sem PK, FK sem índice, nome fora do padrão |
| Linhagem e impacto | Mostra o que é afetado se um objeto mudar e de onde um dado vem |

### Por que domínios importam

Sem domínio, o CPF pode estar como `VARCHAR(14)` em uma tabela, `CHAR(11)` em outra e `NUMBER` em uma terceira. Com um domínio, todas as colunas de CPF seguem o mesmo tipo e regra, e uma mudança no domínio se propaga para o modelo inteiro.

### Como estou estudando sem licença

## 9. SQL

### Categorias de comandos

| Categoria | Significado | Comandos |
| --- | --- | --- |
| DDL | Data Definition Language | `CREATE`, `ALTER`, `DROP`, `TRUNCATE` |
| DML | Data Manipulation Language | `INSERT`, `UPDATE`, `DELETE`, `MERGE` |
| DQL | Data Query Language | `SELECT` (às vezes classificado dentro de DML) |
| DCL | Data Control Language | `GRANT`, `REVOKE` |
| TCL | Transaction Control Language | `COMMIT`, `ROLLBACK`, `SAVEPOINT` |

```sql
-- DDL
CREATE TABLE cliente (
    id_cliente INT PRIMARY KEY,
    cpf        CHAR(11) NOT NULL UNIQUE,
    nome       VARCHAR(100) NOT NULL
);
ALTER TABLE cliente ADD email VARCHAR(150);
TRUNCATE TABLE cliente_staging;
DROP TABLE cliente_temp;

-- DML
INSERT INTO cliente (id_cliente, cpf, nome) VALUES (1, '12345678901', 'Ana');
UPDATE cliente SET nome = 'Ana Souza' WHERE id_cliente = 1;
DELETE FROM cliente WHERE id_cliente = 1;

-- DCL
GRANT SELECT ON cliente TO usuario_leitura;
REVOKE SELECT ON cliente FROM usuario_leitura;

-- TCL
BEGIN TRANSACTION;
UPDATE conta SET saldo = saldo - 100 WHERE id = 1;
SAVE TRANSACTION antes_credito;   -- Oracle: SAVEPOINT antes_credito;
UPDATE conta SET saldo = saldo + 100 WHERE id = 2;
COMMIT;                           -- ou ROLLBACK;
```

### DELETE x TRUNCATE x DROP

| Comando | Categoria | O que remove | WHERE | Dispara trigger | Observação |
| --- | --- | --- | --- | --- | --- |
| `DELETE` | DML | Linhas | Sim | Sim | Registra cada linha no log; pode ser desfeito com ROLLBACK |
| `TRUNCATE` | DDL | Todas as linhas | Não | Não | Muito mais rápido; reinicia a identidade no SQL Server |
| `DROP` | DDL | A tabela inteira (estrutura e dados) | Não | Não | O objeto deixa de existir |

### Oracle x SQL Server (T-SQL)

| Assunto | Oracle | SQL Server / T-SQL |
| --- | --- | --- |
| Tratar nulo | `NVL(col, 0)` | `ISNULL(col, 0)` (`COALESCE` funciona nos dois) |
| Data atual | `SYSDATE` | `GETDATE()` / `SYSDATETIME()` |
| Limitar linhas | `FETCH FIRST 10 ROWS ONLY` | `TOP 10` ou `OFFSET ... FETCH` |
| Autoincremento | `SEQUENCE` ou `IDENTITY` (12c+) | `IDENTITY` ou `SEQUENCE` |
| Texto | `VARCHAR2` | `VARCHAR` / `NVARCHAR` |
| Tratamento de erro | `EXCEPTION` (PL/SQL) | `TRY...CATCH` |
| Variáveis | `v_total NUMBER;` | `DECLARE @total INT;` |
| Transação | Começa implicitamente; exige `COMMIT` | Autocommit por padrão; `BEGIN TRAN` abre transação |
| Concatenação | `\|\|` | `+` ou `CONCAT()` |

Exemplo de transação com tratamento de erro em T-SQL:

```sql
BEGIN TRY
    BEGIN TRAN;
    UPDATE conta SET saldo = saldo - 100 WHERE id = 1;
    UPDATE conta SET saldo = saldo + 100 WHERE id = 2;
    COMMIT;
END TRY
BEGIN CATCH
    IF @@TRANCOUNT > 0 ROLLBACK;
    THROW;
END CATCH;
```

### Transações: ACID e isolamento

- **Atomicidade:** tudo ou nada.
- **Consistência:** a transação leva o banco de um estado válido a outro.
- **Isolamento:** transações simultâneas não interferem indevidamente.
- **Durabilidade:** após o commit, o dado persiste.

Níveis de isolamento: `READ UNCOMMITTED` (permite leitura suja), `READ COMMITTED`, `REPEATABLE READ`, `SERIALIZABLE` e, no SQL Server, `SNAPSHOT`.

### SQL avançado

Os exemplos usam sintaxe de SQL Server; as diferenças para Oracle estão comentadas quando relevantes.

**CTE (Common Table Expression)**

```sql
WITH vendas_2026 AS (
    SELECT id_cliente, SUM(valor) AS total
    FROM venda
    WHERE data_venda >= '2026-01-01'
    GROUP BY id_cliente
)
SELECT c.nome, v.total
FROM vendas_2026 v
JOIN cliente c ON c.id_cliente = v.id_cliente;
```

**ROW_NUMBER e RANK**

```sql
SELECT id_cliente, valor,
       ROW_NUMBER() OVER (ORDER BY valor DESC) AS posicao_unica,
       RANK()       OVER (ORDER BY valor DESC) AS posicao_com_empate
FROM venda;
```

`ROW_NUMBER` numera sem repetir. `RANK` repete a posição em empates e pula a seguinte (1, 2, 2, 4). `DENSE_RANK` não pula (1, 2, 2, 3).

**LAG e LEAD**

```sql
SELECT mes, faturamento,
       LAG(faturamento)  OVER (ORDER BY mes) AS mes_anterior,
       LEAD(faturamento) OVER (ORDER BY mes) AS mes_seguinte
FROM faturamento_mensal;
```

**SUM OVER (acumulado)**

```sql
SELECT mes, faturamento,
       SUM(faturamento) OVER (ORDER BY mes ROWS UNBOUNDED PRECEDING) AS acumulado
FROM faturamento_mensal;
```

**GROUPING SETS e ROLLUP (subtotais)**

```sql
-- ROLLUP: total por região e produto, subtotal por região e total geral
SELECT regiao, produto, SUM(valor) AS total
FROM venda
GROUP BY ROLLUP (regiao, produto);

-- GROUPING SETS: escolho exatamente quais agrupamentos quero
SELECT regiao, produto, SUM(valor) AS total
FROM venda
GROUP BY GROUPING SETS ((regiao), (produto), ());
```

**PIVOT (linhas em colunas)**

```sql
SELECT *
FROM (SELECT regiao, trimestre, valor FROM venda) AS origem
PIVOT (SUM(valor) FOR trimestre IN ([1], [2], [3], [4])) AS p;
-- Oracle: ... PIVOT (SUM(valor) FOR trimestre IN (1, 2, 3, 4))
```

**MERGE (upsert, muito usado em carga incremental)**

```sql
MERGE INTO dim_cliente AS d
USING stg_cliente AS s
    ON d.cpf = s.cpf
WHEN MATCHED THEN
    UPDATE SET d.nome = s.nome, d.cidade = s.cidade
WHEN NOT MATCHED THEN
    INSERT (cpf, nome, cidade) VALUES (s.cpf, s.nome, s.cidade);
```

**CTE recursiva (hierarquia)**

```sql
WITH hierarquia AS (
    SELECT id_funcionario, nome, id_gestor, 1 AS nivel
    FROM funcionario
    WHERE id_gestor IS NULL                 -- ponto de partida: topo
    UNION ALL
    SELECT f.id_funcionario, f.nome, f.id_gestor, h.nivel + 1
    FROM funcionario f
    JOIN hierarquia h ON f.id_gestor = h.id_funcionario
)
SELECT * FROM hierarquia ORDER BY nivel;
-- PostgreSQL exige WITH RECURSIVE; Oracle também tem CONNECT BY
```

## 10. Consistência, particionamento e performance

### Constraints

Constraints garantem a consistência no próprio banco, sem depender da aplicação.

| Constraint | Garante | Exemplo |
| --- | --- | --- |
| `PRIMARY KEY` | Unicidade e não nulo do identificador | `id_cliente` |
| `FOREIGN KEY` | Integridade referencial | `pedido.id_cliente` existe em `cliente` |
| `UNIQUE` | Valor sem repetição | `cpf` |
| `CHECK` | Regra de domínio | `CHECK (qtd > 0)` |
| `NOT NULL` | Preenchimento obrigatório | `nome NOT NULL` |
| `DEFAULT` | Valor padrão | `data_cadastro DEFAULT GETDATE()` |

Na FK, também defino o comportamento na exclusão do pai: `CASCADE` (apaga os filhos), `SET NULL` ou `NO ACTION`/`RESTRICT` (impede a exclusão).

### Particionamento

Particionar é dividir uma tabela grande em partes físicas menores, mantendo uma única tabela lógica para quem consulta.

| Tipo | Divide por | Uso típico |
| --- | --- | --- |
| RANGE | Faixa de valores | Uma partição por mês de venda |
| LIST | Lista de valores | Uma partição por UF |
| HASH | Função hash | Distribuir carga quando não há faixa natural |
| Composto | Combinação (ex.: range + hash) | Tabelas muito grandes com data e alto volume |

Exemplo em Oracle:

```sql
CREATE TABLE venda (
    id_venda   NUMBER,
    data_venda DATE,
    valor      NUMBER(12,2)
)
PARTITION BY RANGE (data_venda) (
    PARTITION p_2026_01 VALUES LESS THAN (DATE '2026-02-01'),
    PARTITION p_2026_02 VALUES LESS THAN (DATE '2026-03-01'),
    PARTITION p_2026_03 VALUES LESS THAN (DATE '2026-04-01')
);
```

No SQL Server, o mesmo conceito usa uma *partition function* (define as faixas) e um *partition scheme* (define onde cada partição fica).

**Conceitos-chave:**

- **Partition pruning:** o banco lê apenas as partições necessárias. Uma consulta de março lê só a partição de março.
- **Índice local:** um índice por partição; facilita manutenção.
- **Índice global:** um índice sobre a tabela inteira; útil para buscas que não filtram pela chave de partição.
- **Manutenção por partição:** arquivar ou remover um mês inteiro de dados em segundos.

**Particionamento x sharding:** particionamento divide a tabela **dentro do mesmo banco**. Sharding distribui os dados entre **servidores diferentes**.

### Roteiro para investigar performance

1. **Analisar o plano de execução** (`EXPLAIN PLAN` no Oracle; plano estimado e real no SQL Server).
2. **Verificar full scans** desnecessários em tabelas grandes.
3. **Verificar joins:** tipo de join, ordem e volume de linhas em cada etapa.
4. **Verificar filtros:** se o `WHERE` reduz cedo o volume de dados.
5. **Verificar sargabilidade:** funções aplicadas na coluna impedem o uso de índice.
6. **Avaliar índices:** existentes, faltantes, compostos (a ordem das colunas importa) e de cobertura.
7. **Verificar estatísticas:** desatualizadas levam o otimizador a escolher planos ruins.
8. **Somente depois** considerar particionamento, desnormalização ou views materializadas.

Exemplo de sargabilidade:

```sql
-- Não sargável: a função na coluna impede o uso do índice
WHERE YEAR(data_venda) = 2026

-- Sargável: filtro direto na coluna
WHERE data_venda >= '2026-01-01' AND data_venda < '2027-01-01'
```

Lembrete: índices aceleram leitura, mas deixam `INSERT`, `UPDATE` e `DELETE` mais lentos e ocupam espaço.

### VLDB

**VLDB (Very Large Database)** é um banco tão grande, normalmente na casa dos terabytes, que operações comuns (consultar, fazer backup, criar índice) precisam ser planejadas. As estratégias mais comuns são particionamento, compressão, arquivamento de dados históricos, cargas em lote fora do horário de pico, paralelismo e monitoramento contínuo de crescimento e consultas mais caras.

### Fluxo de dados

```text
Fonte
  ↓
Staging
  ↓
Validação
  ↓
Transformação
  ↓
Data Warehouse
  ↓

```

### Conceitos

| Conceito | Definição |
| --- | --- |
| ETL | Extrai, transforma e depois carrega no destino |
| ELT | Extrai, carrega bruto e transforma no destino (comum em nuvem e lakehouse) |
| Full load | Recarrega todos os dados a cada execução |
| Incremental | Carrega apenas o que mudou desde a última carga |
| CDC | Change Data Capture: captura inserções, alterações e exclusões na origem |
| Staging | Área intermediária que recebe o dado bruto para validação |
| Qualidade | Verificações de nulos, duplicidade, tipos, órfãos e regras de negócio |
| Origem x destino | Conciliação: contagens e somas batem entre a fonte e o destino? |

Um documento de **especificação de ETL** costuma trazer, para cada coluna: origem, regra de transformação, destino, tipo e o que fazer com registros rejeitados.

Já trabalhei esses conceitos em projeto acadêmico de **Arquitetura Medallion** (camadas Bronze, Silver e Gold), que segue a mesma lógica: dado bruto, dado tratado e dado pronto para consumo.

### Formatos de origem

| Formato | Tipo | Pontos de atenção |
| --- | --- | --- |
| XML | Semiestruturado | Hierarquia de tags; validação por XSD; leitura com XPath; níveis viram tabelas pai e filha |
| JSON | Semiestruturado | Objetos aninhados e arrays precisam ser "achatados"; o esquema pode variar entre registros |
| CSV | Estruturado | Delimitador, aspas, encoding (UTF-8 x Latin-1), separador decimal |
| TXT posicional | Estruturado | Cada campo tem posição e tamanho fixos; depende de layout documentado |
| VSAM | Estruturado (mainframe) | Ver abaixo |

### VSAM: introdução

> VSAM é um dos meus pontos de estudo. Ainda não tenho experiência prática com esse tipo de arquivo; o resumo abaixo reúne os conceitos introdutórios que estou aprendendo.

- **Mainframe:** plataforma de grande porte, comum em bancos e órgãos públicos, onde os arquivos VSAM são usados.
- **VSAM (Virtual Storage Access Method):** método de organização e acesso a arquivos no mainframe.
- **COBOL copybook:** descreve o layout do registro (campos, tamanhos e tipos). Sem ele não dá para interpretar o arquivo.
- **EBCDIC:** codificação de caracteres do mainframe, diferente de ASCII/UTF-8; precisa de conversão.
- **COMP-3:** formato de decimal compactado (*packed decimal*), que armazena dois dígitos por byte e precisa ser convertido antes da carga.
- **Tipos de arquivo VSAM:**
  - **KSDS** (Key Sequenced Data Set): acesso por chave.
  - **ESDS** (Entry Sequenced Data Set): registros na ordem de gravação.
  - **RRDS** (Relative Record Data Set): acesso pela posição do registro.

Fluxo conceitual de integração: ler o arquivo com base no copybook, converter EBCDIC, tratar os campos COMP-3 e carregar na staging para validação.

### Tipos de dado e ambientes

- **Estruturado:** tabelas relacionais, CSV, arquivos posicionais.
- **Semiestruturado:** JSON, XML.
- **Não estruturado:** texto livre, PDF, imagens.

| Ambiente | Foco | Exemplos |
| --- | --- | --- |
| Relacional (OLTP) | Transações, dados normalizados | Oracle, SQL Server, DB2, PostgreSQL |
| Analítico (OLAP) | Consultas e agregações, dados desnormalizados | Data Warehouse, Data Mart, lakehouse |
| NoSQL documento | Esquema flexível | MongoDB |
| NoSQL chave-valor | Acesso rápido por chave | Redis |
| NoSQL colunar / grafo | Grande volume / relações complexas | Cassandra / Neo4j |

| Prática | Em resumo |

### LGPD aplicada a dados

| Conceito | Definição |

## 14. Perguntas da etapa técnica

**1. Diferença entre modelo conceitual, lógico e físico?**
Conceitual representa o negócio, sem tecnologia. Lógico estrutura os dados em tabelas, chaves e relacionamentos, sem banco específico. Físico implementa em um SGBD, com tipos, índices e partições.

**2. O que é 1FN?**
Cada campo tem um valor atômico, sem grupos repetidos ou listas na mesma coluna.

**3. O que é 2FN?**
Está na 1FN e todo atributo não chave depende da chave primária inteira. Só pode ser violada em chave composta (dependência parcial).

**4. O que é 3FN?**
Está na 2FN e nenhum atributo não chave depende de outro atributo não chave (sem dependência transitiva).

**5. Quando desnormalizar?**
Em ambientes analíticos ou consultas de leitura intensa em que os joins pesam. A redundância deve ser intencional, documentada e controlada.

**6. O que é uma chave surrogate?**
Uma chave artificial, sem significado de negócio, gerada pelo sistema (sequence, identity). É estável e compacta; a chave natural costuma ficar como `UNIQUE`.

**7. O que é engenharia reversa?**
Gerar o modelo a partir de um banco ou script existente. Útil para documentar e entender sistemas legados.

**8. O que é engenharia direta (forward engineering)?**
Gerar o banco, ou o script DDL, a partir do modelo físico.

**9. Como investigar uma consulta lenta?**
Plano de execução, full scans, joins, filtros, sargabilidade, índices e estatísticas. Só depois considerar particionamento ou desnormalização.

**10. O que é particionamento?**
Dividir uma tabela grande em partes físicas, mantendo uma tabela lógica. Melhora consultas (partition pruning) e manutenção.

**11. Diferença entre DELETE, TRUNCATE e DROP?**
`DELETE` remove linhas com filtro, gera log por linha e dispara triggers. `TRUNCATE` remove todas as linhas de forma rápida, sem filtro e sem triggers. `DROP` remove a tabela inteira.

**12. Como integrar dados de formatos diferentes em um Data Warehouse?**
Cada fonte entra na staging com o leitor adequado (copybook para VSAM, achatamento para JSON, layout para posicional). Depois padronizo tipos e chaves, valido a qualidade e carrego fatos e dimensões.

**13. Qual a diferença entre OLTP e OLAP?**
OLTP é transacional, normalizado e otimizado para escrita e operações do dia a dia. OLAP é analítico, desnormalizado e otimizado para consultas e agregações.

**14. O que é SCD Tipo 2?**
Uma forma de manter histórico em dimensões: em vez de sobrescrever, cria uma nova linha com período de vigência.

**15. Qual a diferença entre ETL e ELT?**
No ETL, a transformação acontece antes da carga. No ELT, o dado é carregado bruto e transformado dentro do destino.

**16. Como controlar o acesso a uma tabela com dados pessoais?**
Menor privilégio, acesso por role, views que expõem apenas o necessário, mascaramento fora de produção e auditoria, respeitando a finalidade e a necessidade previstas na LGPD.

**17. O que é um domínio em ferramentas de modelagem?**
Um tipo padronizado e reutilizável, que garante que a mesma informação tenha o mesmo tipo e as mesmas regras em todo o modelo.

**18. Qual a diferença entre índice clustered e non-clustered?**
O clustered define a ordem física dos dados na tabela (só existe um). O non-clustered é uma estrutura separada que aponta para as linhas (pode haver vários).

**19. O que é integridade referencial?**
A garantia de que uma FK sempre aponta para um registro existente na tabela referenciada, implementada por constraints `FOREIGN KEY`.

**20. Anonimização e pseudonimização são a mesma coisa?**
Não. A anonimização é irreversível e o dado deixa de ser pessoal. A pseudonimização é reversível com informação adicional e o dado continua sendo pessoal.

### Exercício prático para treinar

Em 20 minutos, modelar um sistema de **agendamento de consultas em uma unidade de saúde**, com paciente, médico, especialidade, unidade, agenda e consulta. Entregar: entidades, cardinalidades, PKs e FKs, normalização até a 3FN e duas regras de negócio implementadas como `CHECK` ou `UNIQUE`.
